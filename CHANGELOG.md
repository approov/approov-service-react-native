# Changelog

## Unreleased

- **Documented: the Expo config plugin initializes and configures nothing**: its native initialization passes only the account ID and comment. The app configures Approov afterwards, from JavaScript after `await ApproovService.initialize(...)` (which resolves at once when the native initialization already ran with the same account ID and comment) or natively. plugin/README.md gains a *Configuration* section: the order is initialize, then configure, and a request processed before the configuration call uses the defaults in force at that moment (`CLOSE_FAILURE`, `Approov-Token` with no prefix, no exclusions or substitutions, signing off, logging `INFO`), with the startup request sources that can hit this (expo-updates, react-native-nitro-fetch `prefetchOnAppStart`, native SDKs, Android headless JS tasks, JavaScript modules that fetch at import time). The plugin ships with the React Native release built on the universal packages. No code change.
- **Added: Expo config plugin for the universal Approov packages**: `app.plugin.js` configures an Expo app's generated projects for the 3.8.0 universal packages. Android: `io.approov:service.android` and its Gradle plugin `io.approov.gradle` (`io.approov:service.android-gradle-plugin`, on the buildscript classpath and applied after `com.android.application`), from Maven Central at `android.version`, with optional `android.repositories`, `android.gradlePluginPath` and `android.cronetDependencyPackages`; the account ID and optional comment as manifest meta-data `io.approov.ACCOUNT_ID` and `io.approov.INIT_COMMENT`; a guarded `ApproovService.initialize` after `super.onCreate()` in `MainApplication` (Kotlin or Java). The account ID comes from `accountId` or the `APPROOV_ACCOUNT_ID` environment variable and is required at prebuild while `nativeInitialize` is true. Options, the files it changes, EAS notes and the interplay with JavaScript initialization are in [plugin/README.md](plugin/README.md). The package's own 3.5.x native module must not be linked next to the universal packages; the README shows the `react-native.config.js` exclusion.
- **Fixed: Expo config plugin values reach the app unchanged**: the Android build compiles a manifest meta-data value that looks like a number, boolean, color or resource reference to that type (`007` became `7`, `#fff` a color, `@null` null, `@string/x` failed the build) and drops a lone backslash, and Xcode expands `$(NAME)`, `${NAME}` and `$NAME` in `Info.plist` values. A comment such as `007` or one containing `\` or `$` therefore reached the SDK altered, so the native initialization used a different comment from the configured one and a JavaScript `initialize` with the configured comment was rejected by the SDK. The plugin now writes the first character of each meta-data value as a `\uXXXX` escape and doubles backslashes, and writes `$` as `$$` in `Info.plist`; a test compiles the result with `aapt2` (when the Android SDK is installed) and checks the exact strings, a 32,768 character account ID included. Account IDs of the documented form `#your-account#...` were not affected.
- **Fixed: Expo config plugin adds the network permissions**: `android.permission.INTERNET` and `android.permission.ACCESS_NETWORK_STATE`, which the Android package requires and neither it nor the Approov SDK declares, are added to the manifest when missing.
- **Changed: Expo config plugin validation**: control characters in `accountId` or `comment` and a dynamic `android.version` (`+`, `latest.`) fail the prebuild with a message naming the option.
- **Fixed: the Expo config plugin is built when the package is packed**: `plugin/build` is git-ignored, so `prepack` now runs `build:plugin`; a package packed from a clean checkout previously had no `plugin/build` and `app.plugin.js` failed to load. `npm test` now runs the plugin tests (`test:plugin`).
- **Added: Expo config plugin native iOS initialization with the universal iOS layer**: the plugin adds two pods to the app target in the Podfile, both from GitHub at a tag because neither is published to CocoaPods trunk: `approov-ios-sdk` (`:git => 'https://github.com/approov/approov-ios-sdk.git'`, `:tag => ios.sdkVersion`, default `3.5.3`) and the universal iOS layer `approov-service-ios` (`:git => 'https://github.com/approov/approov-service-ios.git'`, `:tag => ios.version`, default `3.8.0`, or `:path => ios.podPath` for a local `approov-service-ios` checkout; `ios.version` and `ios.podPath` are not both allowed). The SDK is named in the Podfile because the layer's podspec depends on it by version only and a podspec cannot carry a git source. The plugin also inserts `import ApproovService` plus a guarded `ApproovService.initialize` at the start of `application(_:didFinishLaunchingWithOptions:)` in the Swift AppDelegate (Expo SDK 53 and later), before the React Native factory is created. It reads `ApproovAccountID` and the optional `ApproovInitComment` from Info.plist; on an error it logs only the error type and continues in bypass mode (`initialize("")`), then logs both enabled flags. `nativeInitialize: false` leaves the AppDelegate untouched (the pod and the Info.plist keys are still written). The Objective-C AppDelegate of Expo SDK 52 and earlier fails prebuild with a clear message unless `nativeInitialize` is false. Every insertion is tagged, so prebuild replaces it rather than duplicating it.
- **Changed: Expo config plugin takes one `android.version` for the Android library and Gradle plugin**: the library is `io.approov:service.android` and the Gradle plugin `io.approov:service.android-gradle-plugin`, both from Maven Central, always at the same version (default `3.8.0`). The separate `android.serviceDependency` and `android.gradlePluginDependency` options are removed so the two cannot drift. The Gradle plugin fails the build when the app resolves a library version different from its own. For a local build use `android: { version: '3.8.0-local', repositories: ['mavenLocal', 'mavenCentral'] }`; apps declare the plugin through the generated buildscript classpath (`classpath("io.approov:service.android-gradle-plugin:<version>")`), not a `plugins {}` version.

## [3.5.18] - 2026-10-05

- **Added: Jest mock for app unit tests**: `@approov/approov-service-react-native/jest` is a CommonJS mock of the package that loads under Jest (including `jest-expo`) without transform settings or the native module. Register it with `jest.mock` in a setup file; see "Testing with Jest" in USAGE.md.
- **Fixed: Approov no longer blocks the main thread on a token fetch (iOS)**: a request reaching `interceptRequest:` on the main thread waited for `fetchApproovTokenAndWait:`, which can take seconds on a poor network, so the app froze and the iOS watchdog killed it (`0x8badf00d`, "Fatal App Hang"). A production app saw this from Firebase's `GDTCCTUploadOperation`, which starts its upload tasks on the main queue (approov/approov-service-react-native#43). Approov processing is now skipped on the main thread: the request is forwarded unmodified, with no token, trace ID, secure string substitution or signature, and a warning is logged. The warning means a request that Approov would normally protect went out unprotected, so start such requests from a background thread. Requests on any other thread are unchanged. Covered by a new mini-SDK test that intercepts a request on the main thread; the suite now runs on a worker thread, as protected requests do.
- **Changed: `GDTCCTUploadOperation` is no longer in the default allow list (iOS)**: Firebase's transport upload delegate was intercepted by default, which wrapped its session in the Approov pinning delegate and fetched a token for every upload, although those endpoints are not Approov protected. It is now left alone, so its session and callbacks are untouched. An app that does need Approov on that session can restore the old behaviour with `ApproovService.addAllowedDelegate("GDTCCTUploadOperation")`.
- **Fixed: `handlePinningShouldProcessRequest` is now honoured on both platforms**: the hook was declared on both service mutator interfaces but never called, so a custom mutator could not skip Approov pinning for a host (approov/approov-service-react-native#35, approov/core-project-approov#716). Android now calls it from the pinning network interceptor for every HTTPS exchange, with the full request. iOS calls it from the pinning delegate once per TLS connection, with a request for the connection's origin (`https://host:port/`), because server trust is a connection-level challenge. Returning `false` skips only the Approov pin check; normal TLS trust evaluation still applies. On iOS the decision holds for the connection and the requests that reuse it; on Android each request is checked against the mutator in force. The default and policy mutators keep pinning every request, so nothing changes unless a custom mutator overrides the hook. Supersedes the documentation-only #36.
- **Fixed: redirects carried the Approov token and substituted secrets to the redirect target (iOS, security-relevant)**: URLSession builds a redirect request from the previous attempt's headers, and the pinning delegate only re-signed it, so a redirect from a protected API to any other host was sent the token, trace ID, signature and substituted secure strings issued for the original host, with the token re-signed for the new URL. A redirect is now classified afresh, since Approov protection is decided per API domain: everything Approov added for the previous attempt is taken back out (headers it added are removed, substituted headers and query parameters go back to their placeholders), then the follow-up is processed like a new request. A redirect to a host Approov does not protect carries none of it; one to a protected API gets a token, substitutions and a signature for the new URL; a 303 after a POST is signed as the GET it becomes. The token fetch for the follow-up runs off the session's delegate queue. If processing the follow-up fails, the task fails with the same error a first request would get (`499`, or `503` for a network status) rather than returning the redirect response as if it were final; a session without the mock protocol (`fetchWithApproov`) cancels the task. Requests sent by `fetchWithApproov` are covered too, and a redirect of a request with no record of what Approov applied still drops the Approov token and trace ID. The record is kept as NSURLProtocol properties holding SHA-256 digests of the applied values, never the token, signatures or secrets themselves. Covered by new mini-SDK tests for redirects to unprotected and protected hosts, a 303 to the same URL with the secure strings rotated between attempts, and a caller delegate that is offered the redirect.
- **Fixed: redirects carried the Approov token and substituted secrets to another origin (Android, security-relevant)**: OkHttp follows redirects below the application interceptors and builds the follow-up from the previous request's headers, so a redirect from a protected API to any other host was sent the token, trace ID, signature and substituted secure strings issued for the original host. Approov credentials now never leave the origin (scheme, host and port) they were issued for: the pinning network interceptor removes every header that still carries a value Approov set from an attempt to another origin, including a same-host redirect from `https` to `http` or to another port. A follow-up to another origin is not protected again. A header the app set to its own value on a new request built from `Response.request()` is kept.
- **Fixed: expo-fetch requests were sent without Approov protection (iOS)**: `expo/fetch`, the default `fetch` from Expo SDK 56, opens its own `URLSession` with an `ExpoModulesCore.URLSessionSessionDelegateProxy` delegate, which was not in the default allow list, so its requests carried no Approov token and were not pinned. That delegate is now intercepted by default; no `addAllowedDelegate` call is needed.
- **Fixed: tasks on an allowlisted session could stall forever (iOS)**: the pinning delegate forwarded `URLSession:task:willPerformHTTPRedirection:newRequest:completionHandler:` and `URLSession:dataTask:didReceiveResponse:completionHandler:` only when the app's delegate implemented them, and otherwise never called the completion handler. Because the pinning delegate itself implements both, URLSession waits for that handler, so a delegate implementing only some optional callbacks (ordinary for a session added with `addAllowedDelegate`) left every delegate-routed task hanging, and every redirect on such a session never completed. Both handlers are now completed with URLSession's default (follow the redirect, allow the response) when the app's delegate does not implement the callback. React Native's own networking implements both callbacks and was not affected. Same defect as `approov-service-urlsession` 3.5.14 (TESTING_REQUIREMENTS 4b).

- **Changed: debug builds forward local development hosts untouched (Android and iOS)**: only the host name `localhost` used to bypass the interceptor, so Metro traffic on the Android emulator alias `10.0.2.2` or on `127.0.0.1` went through the full pipeline, cost a token fetch per request and came back as `BAD_URL`, which the default policy fails. In a debuggable Android app, `127.0.0.1`, `::1`, `10.0.2.2` and `10.0.3.2` are now forwarded without any Approov processing, like `localhost`; on iOS, in a build compiled with `DEBUG`, `127.0.0.1` and `::1` are. Release builds are unchanged. Metro on a physical device uses the development machine's LAN address and still needs `addExclusionURLRegex`. Reported by a customer against 3.5.17. Tracked as approov/core-project-approov#810.
- **Fixed: documentation told apps to configure the service before initialization**: REFERENCE.md advised calling `setTokenHeader`, `setTraceIDHeader`, `setBindingHeader`, `addSubstitutionHeader`, `addSubstitutionQueryParam`, `addExclusionURLRegex` and `setSuppressLoggingUnknownURL` inside `ApproovProvider`'s `onInit`, "prior to Approov initialization". `onInit` runs before `initialize`, and every successful `initialize()` resets that configuration on both platforms, so it was discarded, and a binding header set there left tokens unbound. The docs now say to apply it after initialization, keyed on `approovInitCount` (new USAGE.md section *Configuration Is Reset By Initialization*). No code change. Tracked as approov/core-project-approov#810.
- **Changed: WebSocket upgrades no longer carry the Approov token (Android)**: WebSockets are not supported. React Native's own WebSocket module builds a separate OkHttp client that Approov does not configure, so it is not affected. A WebSocket opened through the shared client from `OkHttpClientProvider` (as some libraries do) passes through Approov's application interceptor, but OkHttp skips network interceptors, and so the pin check, for WebSocket upgrades. So that a token never travels over a connection Approov has not pinned, such an upgrade request (`Upgrade: websocket`) is forwarded untouched: no token, secure string substitution or signature. Do not rely on an Approov token to authorize WebSockets. iOS is unaffected (React Native uses SocketRocket, which the service layer does not intercept). GraphQL queries and mutations over HTTPS are unchanged and fully protected. Covered by `ApproovWebSocketUpgradeTest`.
- **Changed: one log level for every native log line, consistent across platforms (Android and iOS)**: `setLogLevel` now controls all logging. On Android, per-request lines in the interceptor, the pin builder and message signing wrote to Logcat directly, and on iOS the Swift mutator bridge, the Swift message signer and the nil-delegate warning did the same, so `setLogLevel(NONE)` did not silence them. The same event now uses the same level on both platforms: per-request detail such as `token for <url>` (which includes the device ID and client IP) is DEBUG, lifecycle events are INFO, and a factory or custom builder that could not be read, `setCustomClientBuilder` failures and deprecated no-op calls are WARN. On iOS, INFO lines now use the default `os_log` type, so they are shown in Console.app without enabling info messages. A unit test fails if raw logging is added again. See LOGGING.md for the level policy. Per-request and per-connection lines (`request mutation`, `task mutation`, `intercepting`, `observed dataTask`, excluded URLs, pin checks) are DEBUG on both platforms, so release builds at the default INFO level do not log full URLs for every request. Bypass mode logs INFO for the first forwarded request and DEBUG after that. The iOS redirect line logs the URL with its placeholders, not substituted secure strings.
- **Fixed: `getPinningDiagnostics()` showed obfuscated interceptor names in minified builds (Android)**: the consumer rules now keep the names of `ApproovInterceptor` and `ApproovPinningInterceptor`, so the `interceptors` list stays readable. The presence flags were already correct.
- **Fixed: a pin loading failure during `initialize()` no longer leaves the service initialized (Android)**: the service marked itself initialized before loading the new pins, so if loading failed the promise rejected but requests still carried tokens over connections checked against the previous, possibly empty, pin set. Pins are now built before any state is committed and installed together with it; on failure nothing changes and the promise rejects.
- **Changed: requests sent before `initialize()` completes log one warning, not an error per request (Android and iOS)**: the first such request logs a warning with the guidance to await `initialize()`; later ones, including Metro's own dev traffic, log at debug level through the level-gated logger. Behaviour is unchanged: the requests are still forwarded without a token.
- **Deprecated: pin change listener and startup-window Java API (Android)**: `ApproovService.PinChangeListener`, `addPinChangeListener`, `getPinChangeListeners`, `notifyPinChangeListeners`, `setEarliestNetworkRequestTime`, `getEarliestNetworkRequestTime`, `ApproovClientBuilder.approovPinsUpdated` and the `ephemeral` constructor flag of `ApproovClientBuilder` are deprecated. Existing native code still compiles. Clients share one pin state that initialization and SDK configuration updates refresh, so there is nothing to rebuild; registered listeners are still called after a refresh. The startup window no longer exists, so `getEarliestNetworkRequestTime` returns 0: await `ApproovService.initialize()` before protected requests instead. The JavaScript API is unchanged.
- **Fixed: minified Android apps failed in `initialize()` (R8)**: the Approov SDK AAR ships no R8 rules and its native library looks up Java members by name, so R8 removed `AttestationServicesResponse.<init>(String, byte[], long, int, int)` and `initialize()` threw `no non-static method ...`. The consumer rules now keep the whole `com.criticalblue.approovsdk` package and suppress warnings for the optional Play Integrity and Play services tasks classes it references. Apps no longer need their own SDK keep rule. This is a stop-gap until the SDK ships its own rules (approov/core-project-approov#807). Present in 3.5.17 as well.
- **Fixed: `updateClientFactory(true)` kept a stale client when another SDK had installed its factory later (Android)**: recovery copied the NetworkingModule's live client, which was built before the other SDK's factory existed, and then installed an Approov factory over it, so that SDK's settings were lost for the rest of the process, including after reloads. Recovery now builds from the installed third-party factory, as a reload would, keeps React Native's cookie jar, and wraps the factory so it also survives later context recreations. Present in 3.5.17 as well.
- **Fixed: a rebuilt OkHttp client kept fetching tokens through a stale `ApproovService` (Android, security-relevant)**: `ApproovClientBuilder.apply()` guarded against double-registration by skipping its interceptor whenever *any* `ApproovInterceptor` was already present on the builder. That class-level check cannot distinguish the live interceptor from a stale one added by a previously wrapped `OkHttpClientFactory`, so when the React Native context is recreated at runtime (for example by an Expo OTA reload) the freshly built `ApproovService` was skipped and the client retained its old, dead interceptor, sending requests with a missing `Approov-Token`. `apply()` now removes every `ApproovInterceptor` already on the builder and then adds the current one, guaranteeing the client uses this service's interceptor; this also stops interceptors accumulating across successive rebuilds. Third-party interceptors (New Relic and similar) are left untouched. Reported by a customer; covered by a new `ApproovClientBuilderTest` regression that asserts a rebuild leaves exactly one, live, interceptor. iOS is unaffected.
- **Fixed: R8 duplicate class failure when combined with another Approov Android layer**: the structured field value parser and message signing helpers were compiled as `io.approov.util.http.sfv` and `io.approov.util.sig`, the same package names every other Approov Android service layer uses, so an app that also depends on `io.approov:service.okhttp` (or retrofit, volley, httpsurlconn, grpc) failed minified builds with `Type io.approov.util.http.sfv.ByteSequenceItem is defined multiple times`. Both packages now live under `io.approov.internal.reactnative.util`, matching the BouncyCastle relocation, so the React Native AAR carries no `io.approov.util` classes. For React Native plus OkHttp, use React Native service 3.5.18 or newer with `io.approov:service.okhttp:3.5.8` or newer; no class-removal patch is needed. The JavaScript API is unchanged, but native Android callers of `ApproovDefaultMessageSigning.SignatureParametersFactory.setBaseParameters` must switch imports from `io.approov.util.sig.SignatureParameters` to `io.approov.internal.reactnative.util.sig.SignatureParameters` and recompile. Tracked as approov/core-project-approov#770.
- **Fixed: React Native networking reflection survives R8 (Android)**: consumer rules now keep the `OkHttpClientProvider` factory field and the `NetworkingModule` client, custom client builder and cookie fields (Java `m`-prefixed and Kotlin names). Without them R8 could rename those members in a minified app, and Approov would silently fail to find and wrap another SDK's OkHttp factory or custom client builder.
- **Fixed: duplicate symbol `_isInitialized` when linking with other static libraries (iOS)**: `ApproovService.m` defined its module state (`isInitialized`, `initialConfigString`, `pendingPrefetch`, `useApproovStatusIfNoToken`, `suppressLoggingUnknownURL`, the header and prefix names, the substitution and exclusion collections, and the `sSPKIHeaders` table) as file-scope variables with external linkage, so each was exported as a global C symbol from `libapproov-service-react-native.a`. Any other static library exporting the same name (for example the HyBid ad SDK, which also exports `_isInitialized`) fails the app link with `ld: duplicate symbols`. All thirteen are now `static`, giving them internal linkage; they were only ever accessed from `ApproovService.m`, so behaviour is unchanged. `sSPKIHeaders` was also declared without an initializer, which makes it a common symbol that the linker may silently merge with a same-named variable from another library rather than reporting a duplicate. Reported by a customer building against HyBid. `ApproovProps.m` no longer exports `PropsResource` and `PropsExtension` either.
- **Fixed: task-level authentication challenges reach the app's delegate (iOS)**: the pinning delegate implemented a challenge method with a selector URLSession never calls, so HTTP Basic and other task-level challenges did not reach a wrapped delegate. It now implements `URLSession:task:didReceiveChallenge:completionHandler:` and forwards those challenges. `handlePinningShouldProcessRequest` is always asked with the connection's origin, with a lowercase host and IPv6 literals in brackets, never a task's request.
- **Changed: verify pins on every HTTPS network exchange (Android)**: pins are checked by a network interceptor against the certificate chain the trust manager verified, not the raw list the server sent, so a certificate appended to a valid chain cannot satisfy a pin and a pinned root CA (managed trust roots) matches. The pinning interceptor is the first network interceptor. A mismatch closes an HTTP/1.1 connection; an HTTP/2 connection, which may carry streams for other hosts, is left open and every exchange on it is checked again. Clients share immutable pin state, so repeated checks do not call `getPins()` or rebuild clients.
- **Fixed: forced pin updates no longer abort Android requests**: pins are refreshed once when the configuration-change or force-apply flag is set, then the same request continues through token policy and network pin verification. A pin refresh failure fails that request with an `ApproovException`; it is never thrown as an unchecked exception, which OkHttp would rethrow on its dispatcher thread and end the app. Certificate mismatches still block the request.
- **Changed: hybrid Android interception with shared pins**: application interception handles tokens and substitutions; network interception checks TLS pins. One pinning interceptor serves the whole process, since the SDK's pins are process-wide, so every client, including recovery and `fetchWithApproov` clients and clients built before a React Native reload, sees the current pins. Initialization and SDK configuration updates refresh pins without fetching them during client construction. Customer pins are not merged.
- **Changed: initialization must be awaited (Android and iOS)**: Removed the 2.5-second startup grace periods. Protected request paths must await successful `initialize()` completion; early requests can proceed unprotected. HTTP timeouts are unchanged.
- **Changed: initialization keeps the bundled properties (Android and iOS)**: the token header, prefix and binding header set from `approov.props` (Android) or `approov.plist` (iOS) at launch are now what `initialize()` resets to, instead of the built-in defaults. Before, the first JavaScript `initialize()` silently replaced them with `Approov-Token` and no binding.
- **Added: `ApproovProvider` `onInitialized` callback**: it runs after each successful initialization and before `approovReady` becomes true, so configuration that initialization resets can be applied before protected requests start. If it throws or rejects, the provider reports the error and stays not ready.
- **Fixed: fresh-client recovery preserves React Native cookie handling (Android)**: `updateClientFactory(false)` keeps the active NetworkingModule's cookie container, or supplies and connects one when needed. Cookies continue to flow through React Native after recovery and reload, avoiding the RN 0.76 cookie-container cast failure. Plain OkHttp timeout defaults are unchanged.
- **Fixed: RN 0.79+ discarded another SDK's OkHttp factory (Android)**: the install path read the installed `OkHttpClientProvider` factory via reflection on the field `sFactory`, but `OkHttpClientProvider` became a Kotlin object in React Native 0.79 and the field was renamed `factory`. The lookup silently failed, so Approov replaced the existing factory instead of wrapping it, dropping any other SDK's factory, interceptors and configuration (New Relic, Datadog, etc.). It now reads both `factory` and `sFactory`.
- **Fixed: factory chain leak across reloads (Android, RN <= 0.78)**: on React Native versions where the factory is wrapped (<= 0.78), each service construction wrapped the previously installed factory, so repeated context recreations (e.g. OTA reloads) retained every previous `ApproovService` and its `ReactContext`. The factory is now a named `ApproovOkHttpClientFactory` that records the factory it wraps; a later registration recognises its own previous factory and unwraps it, replacing the Approov layer rather than chaining onto it. Verified on RN 0.76: repeated reloads keep the chain at depth one. This also makes the stale-interceptor case impossible by construction, complementing the `apply()` de-duplication above.
- **Fixed: legacy `setCustomClientBuilder` registration silently skipped (Android)**: the reflective lookup demanded the exact parameter type `NetworkingModule.CustomClientBuilder` (nested), but React Native accepts the top-level `com.facebook.react.modules.network.CustomClientBuilder` on 0.76/0.81 (the nested type extends the top-level one). `getMethod()` matched nothing and the path was skipped as "expected on RN 0.73+". The method is now matched by shape (name + a single parameter assignable from `ApproovClientBuilder`), so the legacy path registers where it applies.
- **Fixed: `isInterceptorActive()` could falsely report protection (Android)**: it inspected `OkHttpClientProvider.getOkHttpClient()`, the provider's cached singleton, rather than the client the `NetworkingModule` actually uses for `fetch()`, which can be a different instance. It now reads the NetworkingModule's live client by reflection (`client` on RN 0.73+, `mClient` on older), falling back to the provider client only if that cannot be read.
- **Fixed: Approov's custom client builder wraps another SDK's instead of replacing it (Android)**: React Native applies this hook per request on a `newBuilder()` of the module's client, so the previously registered builder (`customClientBuilder` / `mCustomClientBuilder`) is read and wrapped, and a previous Approov builder from an earlier context is unwrapped rather than chained. The hook gets its own `ApproovClientBuilder`, separate from the factory path's, so the other SDK's builder runs once per request rather than twice. It is registered with a direct call to `NetworkingModule.setCustomClientBuilder`, which React Native 0.76 and later declare as a public static method.
- **Fixed: diagnostics inspect the effective per-request client (Android)**: `isInterceptorActive()` and `getPinningDiagnostics()` now inspect the client a `fetch()` really runs through (the NetworkingModule's client with the registered custom client builder applied), so they neither report protection that is only on the provider's cached singleton, nor miss protection delivered through the per-request hook.
- **Fixed: `updateClientFactory(true)` recovers from the live client (Android)**: it copied the provider's cached client and then installed the copy on the NetworkingModule, which dropped any interceptor another SDK had added to the live client while still reporting success. It now copies the NetworkingModule's actual client.
- **Fixed: custom client callbacks support non-public implementations and preserve failures (Android)**: requests and diagnostics invoke the public React Native callback interfaces, allowing another SDK's anonymous classes and lambdas to run. Callback exceptions and errors propagate rather than allowing partially configured requests to proceed; diagnostics reject when a callback throws an exception.
- **Fixed: empty certificate pinners no longer report protection (Android)**: `isPinnerPresent` checks for configured pins. A TLS chain cleaner can make an empty pinner differ from `CertificatePinner.DEFAULT` without enforcing any pins.
- **Fixed: earlier `ApproovService` and `ReactContext` instances are no longer retained after a reload (Android)**: a recovery via `updateClientFactory` installs a named factory that a later registration recognises and unwraps, and it keeps a separate base client without Approov interceptors or pins, preserving other SDKs' interceptors and client settings. A previously installed Approov factory or custom client builder is retired on re-registration wherever it now sits, including beneath a third-party wrapper. An `ApproovInterceptor` holds its service weakly and switches to the newest service after a reload, so a client built before the reload (for example a cached or image-loading client) neither keeps the old context alive nor uses its configuration.

## [3.5.17] - 2026-08-25
- **Changed: the out-of-box service mutator is the standard pass-through, and HTTP Message Signing is opt-in**. `ApproovService` now installs `ApproovServiceMutator.DEFAULT` on Android and `ApproovServiceMutatorDefault` on iOS at construction, on `setServiceMutator(null)`, and on the reset performed by a successful initialization. Protected requests still fetch an Approov token, still carry the `Approov-Token` header and are still pinned; they are forwarded **unsigned**. This puts the React Native layer on the same default as the okhttp and urlsession service layers, which install the same pass-through mutator. To sign, opt in from JavaScript with `ApproovService.setServiceMutatorType(mask, { sign: true })`, or install `ApproovDefaultMessageSigning` directly from native code. `MutatorPreset.DEFAULT` now restores the unsigned default mutator, and its `sign` argument remains not applicable.
- **Added: the signature type is selectable from JavaScript**. `setServiceMutatorType(mask, options)` accepts `options.signature`, either `'install'` (the default) or `'account'`, so an app can choose which HTTP Message Signature the installed policy mutator produces without writing native code. `sign: false` continues to forward the request unsigned, and the option is ignored for `MutatorPreset.DEFAULT`. The native bridge signature gains the mode on both platforms (`setServiceMutatorType(mask, sign, signatureMode, promise)` on Android, the matching `signatureMode:` argument on iOS) and `PolicyMutator` gains a constructor selecting the account factory.
- **Documented**: `USAGE.md` and `REFERENCE.md` describe signing as opt-in and no longer present it as default behaviour. The guidance on basing custom mutators on `ApproovServiceMutator.DEFAULT` is restated accordingly: it is the pass-through, and message signing is added by extending or composing with `ApproovDefaultMessageSigning`.

- **Hardened — `setServiceMutatorType` mask validation (security-relevant)**: The proceed bitmask is bridged from JavaScript as a floating-point number and is now rejected on both Android and iOS unless it is a finite, integral, 32-bit value. A fractional, `NaN`/`Infinity`, or out-of-range mask would previously have been silently truncated or coerced by the native narrowing cast, potentially installing a policy other than the one intended; such inputs now reject the promise instead of being applied. Covered by new Android and iOS native regression tests. (Copilot review, PR #32.)
- **Hardened — `setServiceMutatorType` rejects undefined mask bits (security-relevant)**: Only bits 0-10 name an Approov failure status. A mask setting any bit above `DISABLED` (for example `1 << 11`) previously passed validation and installed a policy that granted proceed to nothing — a silent block-everything policy indistinguishable from a deliberate one. Such masks are now rejected on both Android and iOS. The permitted set is exposed as `PolicyMutator.ALL_BITS` on both platforms.
- **Fixed — stale service mutator across a config-change re-initialization (Android, security-relevant)**: `ApproovService.serviceMutator` is now `volatile`. The re-initialization reset wrote it under the instance monitor, but the OkHttp interceptor reads it through the static, unsynchronized `getServiceMutator()`, so that lock established no happens-before relationship for those reads — a request racing a re-initialization could keep using a custom mutator that had already been reset.

Native integrations that relied on `null` to disable signing must now install a mutator that does so explicitly.
- **Changed — policy mutators now apply to secure-string substitution**: A `PolicyMutator` installed via `setServiceMutatorType` previously governed only the token-fetch outcome; the inherited handlers still decided header and query-parameter substitution, so a status the mask permitted to proceed could still block the request when the same status was returned during substitution. This makes `PROCEED_IF_UNAVAILABLE` behave as documented for apps that also use `addSubstitutionHeader`/`addSubstitutionQueryParam`.
- **Documented — `ALWAYS_PROCEED` is not literally every status**: A failure status with no proceed bit always blocks, even under `ALWAYS_PROCEED` — the policy fails closed rather than proceeding on a status it does not recognise. On iOS this applies today to `notInitialized` / `badKey` / `badPayload`, which have no bit. On Android every failure status the current SDK (3.5.3) emits has a bit, so `ALWAYS_PROCEED` proceeds on all of them; a status added by a later SDK without a bit will block under the same fail-closed rule. This matches the okhttp / urlsession layers, which block any token-fetch status they do not explicitly allow.
- **Documented — message signing fail-open/fail-closed rule**: Signing failures proceed with the request unsigned, except for two cases that fail closed: an unsupported signature algorithm, and a required message body digest that cannot be produced. Both surface as a failed request rather than an unsigned one. Signature *unavailability*, base64 and ASN.1/DER decode failures, and header serialization failures all proceed unsigned on both platforms, since they indicate the signature could not be obtained rather than that the request itself is untrustworthy.
